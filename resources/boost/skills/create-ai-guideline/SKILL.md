# Creating and Updating AI Guidelines with Laravel Boost

## What Are Guidelines?

Guidelines are composable instruction files that Laravel Boost loads **upfront** into every agent session. When you run `boost:install` (or `boost:update`), Boost compiles its built-in guidelines plus your custom ones into each selected agent's instruction file (`CLAUDE.md`, `AGENTS.md`, `.junie/`, etc.). Unlike skills, which activate on-demand, guidelines are always present and enforce project-wide standards.

## Guidelines vs Skills

| Aspect | Guidelines | Skills |
|--------|-----------|--------|
| Loaded | Upfront, always present | On-demand, when relevant |
| Scope | Broad, foundational conventions | Focused, task-specific patterns |
| Location | `.ai/guidelines/` | `.ai/skills/{name}/` |
| Format | `.md` or `.blade.php`, no frontmatter | `SKILL.md` with YAML frontmatter |
| Purpose | Core conventions & best practices | Detailed implementation patterns |

Use guidelines for rules that should always apply (coding standards, conventions, architecture decisions). Use skills for domain knowledge that is only relevant during specific tasks. To author a skill instead, use the `create-ai-skill` skill.

## Where Guidelines Live

There are exactly two valid write locations:

1. **Project guidelines** — `.ai/guidelines/` at the project root. This is the normal case.
2. **Third-party package guidelines** — `resources/boost/guidelines/core.blade.php`, used **only** when the user is explicitly maintaining a Composer package that ships guidelines to Boost (this repository is itself such a package).

**CRITICAL:** Write guidelines only to one of those two locations. NEVER create, modify, or delete files in `.claude/`, `.cursor/`, `.agents/`, `.junie/`, or similar directories — they hold autogenerated content managed by external tools. NEVER hand-edit the compiled output files (`CLAUDE.md`, `AGENTS.md`, etc.); Boost regenerates them on every `boost:install`/`boost:update`, so manual edits are overwritten. Edit the source guideline and recompile instead. If you see guideline-like files outside `.ai/guidelines/` or `resources/boost/guidelines/`, leave them untouched.

## File Formats

Guidelines are plain Markdown (`.md`) or Blade (`.blade.php`) files with **no YAML frontmatter** — this is a key difference from skills. Both are picked up automatically by Boost.

- Use `.md` for simple, static rules.
- Use `.blade.php` when you need Blade directives such as `@verbatim` (required around `<code-snippet>` blocks so Blade does not try to compile their contents).

## Directory Structure

```
.ai/
  guidelines/
    core.md                              # Primary project guideline
    api-standards.blade.php              # Blade-templated guideline
    inertia-react/
      2/
        forms.blade.php                  # Override of a Boost built-in guideline
```

For a package that ships guidelines to its users:

```
resources/boost/guidelines/
  core.blade.php                         # Loaded into users' projects on boost:install
```

You can use any number of files; each should cover a distinct area of conventions.

## How Guidelines Are Compiled

`boost:install` and `boost:update` both regenerate the agent instruction files from the full set of guidelines (Boost's built-in set plus your custom ones), wrapping them in Boost's own managed block within each file. Custom guidelines are appended alongside the built-in ones unless they override a built-in path (see below). Because the entire managed block is rewritten on every run, never edit the generated file by hand — edit the source guideline and recompile.

The generated files (`CLAUDE.md`, `AGENTS.md`, `.junie/`, `.mcp.json`, `boost.json`) are safe to add to `.gitignore` since they are reproducible from your guidelines.

## Overriding Boost's Built-in Guidelines

To replace a Boost built-in guideline, create a custom guideline at the **same relative path**. Boost uses your version instead of the default.

```
# Override Boost's Inertia React v2 forms guidance:
.ai/guidelines/inertia-react/2/forms.blade.php

# Override Boost's Livewire core guidance:
.ai/guidelines/livewire/core.blade.php
```

The `core` segment holds version-agnostic guidance; numbered subfolders (`2/`, `3/`, ...) target a specific major version. Match the built-in path exactly — a near-miss creates a new guideline instead of overriding. Recompile after creating or changing an override.

## Third-Party Package Guidelines

When maintaining a Composer package, ship guidelines by adding `resources/boost/guidelines/core.blade.php`. Boost auto-loads it into users' projects. End users pick it up via `boost:install` or `boost:update --discover` — plain `boost:update` will not discover a newly installed package.

Keep package guidelines short: a one-line overview of what the package does, any required conventions, and example usage. Wrap code in `@verbatim`:

```blade
## Package Name

This package provides [brief description of functionality].

### Features

- Feature 1: [clear, short description].
- Feature 2: [clear, short description]. Example usage:

@verbatim
<code-snippet name="How to use Feature 2" lang="php">
$result = PackageName::featureTwo($param1, $param2);
</code-snippet>
@endverbatim
```

## Writing Guidelines

### Content Principles

- **Concise and actionable** — every line tells the agent what to do or not do.
- **Use imperative phrasing** — "Use X" not "You should consider X".
- **Omit what the agent already knows** — do not explain PHP, Laravel, or Eloquent basics.
- **Document project-specific deviations** — capture where this project differs from framework defaults.
- **One authoritative approach** — do not present multiple equivalent options.
- **Use bullet lists** — easier for agents to parse than prose.
- **Keep them short** — guidelines are always loaded, so brevity matters.

### Structure Template

```markdown
## Topic Name

Brief one-line description of what this covers.

### Conventions
- Be specific: "Use `Model::query()` instead of `DB::`" not "prefer Eloquent"
- One rule per bullet

### Code Examples

<code-snippet name="Create a record" lang="php">
public function store(StoreRequest $request): JsonResponse
{
    $model = Model::query()->create($request->validated());

    return response()->json($model, 201);
}
</code-snippet>
```

### Code Snippets

Use Boost's `<code-snippet>` tag for examples. The `name` attribute describes the pattern; `lang` sets syntax highlighting. In `.blade.php` files, wrap snippets in `@verbatim` / `@endverbatim` so Blade does not parse the contents:

```blade
@verbatim
<code-snippet name="Human-Readable Description" lang="php">
// code here
</code-snippet>
@endverbatim
```

### What NOT to Include

- Generic framework documentation — instruct the agent to use the `search-docs` MCP tool instead.
- Long tutorials or explanations — guidelines state rules, not teach concepts.
- Multiple equivalent approaches — pick the preferred one.
- Information that changes frequently (version numbers, dates).

## Updating Existing Guidelines

### When to Update vs. Create a New File

- **Update an existing file** when the change fits an existing category (e.g., a new database rule in a file that already covers database conventions).
- **Create a new file** when the rules cover a distinct area not represented by any existing file.

### Update Workflow

1. List existing files in `.ai/guidelines/` to understand what already exists.
2. Read the relevant file(s) to understand current content, structure, and style.
3. Make the targeted edit — add, modify, or remove rules as requested.
4. Preserve the existing file's organization and formatting style.
5. Recompile and verify (see below).

### Removing Rules

- Delete the rule cleanly.
- Remove any section heading left empty after the deletion.
- If removing the last rule in a file, delete the entire file rather than leaving an empty shell.

### Reorganizing

If an update makes a guideline file too large or unfocused, suggest splitting it into multiple files, each covering a distinct area. Move rules to the appropriate new files and delete the original once fully split.

## Applying Changes

```bash
# Routine: apply edits to existing guidelines (default command)
php artisan boost:update

# First-time setup, or after changing which agents/features are active
php artisan boost:install

# Pick up guidelines/skills from newly installed Composer packages
php artisan boost:update --discover
```

Default to `boost:update` after editing guidelines. Use `boost:install` only for first-time setup or when changing the selected agents/features. Use `boost:update --discover` when a newly installed package should contribute its guidelines.

Automate routine refreshes by adding to `composer.json`:

```json
{
  "scripts": {
    "post-update-cmd": [
      "@php artisan boost:update --ansi"
    ]
  }
}
```

## Gotchas

- The compiled files (`CLAUDE.md`, `AGENTS.md`, etc.) are regenerated on every `boost:install`/`boost:update`. Hand edits are overwritten — change the source guideline in `.ai/guidelines/` and recompile.
- Plain `boost:update` only refreshes already-published resources. It will **not** discover a newly installed package; use `boost:update --discover` (or `boost:install`) for that.
- Overrides require an **exact** path match against the built-in guideline. A near-miss silently creates an extra guideline instead of replacing the default.
- In `.blade.php` guidelines, any `<code-snippet>` (or other literal angle-bracket content) must be wrapped in `@verbatim` / `@endverbatim`, or Blade will try to compile it.

## Verification

After creating or updating a guideline, verify:

1. The file is in `.ai/guidelines/` (or `resources/boost/guidelines/` for a package) with a `.md` or `.blade.php` extension, has NO YAML frontmatter, and starts with a Markdown heading (`# Title`).
2. Nothing was written to `.claude/`, `.cursor/`, `.agents/`, or `.junie/`, and the generated `CLAUDE.md`/`AGENTS.md` were not hand-edited.
3. Code examples use `<code-snippet>` tags with `name` and `lang`; `.blade.php` files wrap them in `@verbatim` / `@endverbatim`.
4. The rules are concise and actionable.
5. If overriding a built-in guideline, the path matches Boost's path exactly.
6. Recompiled via `boost:update` (or `boost:install` / `boost:update --discover` for first-time or new-package discovery).

When updating an existing guideline, also verify:

7. Existing rules that were not meant to change are still intact.
8. No empty sections or orphaned headings were left behind after removals.
9. The file was not moved out of its guidelines directory.

## Key Files

- `.ai/guidelines/` — Custom project guideline directory (create if missing).
- `resources/boost/guidelines/core.blade.php` — Guidelines shipped by a Composer package.
- `CLAUDE.md` / `AGENTS.md` — Compiled output, auto-generated by Boost.
- `boost.json` — Boost configuration file (auto-generated).
- `create-ai-skill` skill — Related skill for authoring on-demand skills.

## Common Pitfalls

- Do not add YAML frontmatter to guideline files — only skills use frontmatter.
- Do not write long, tutorial-style content — guidelines are rules, not documentation.
- Do not place guideline files inside `.ai/skills/` — they will be treated as skills and fail to parse due to missing frontmatter.
- Do not create or modify files in `.claude/`, `.cursor/`, `.agents/`, or `.junie/` — those directories contain autogenerated content managed by external tools.
- Do not overwrite an entire guideline file when only a small edit was requested — make targeted changes and preserve existing content.
